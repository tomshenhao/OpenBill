## Reusable request scope

The six drafts use the existing first-priority wording. The requested data is
general residential product information, nationwide wherever offered, with initial
validation of **all applicable Auckland distribution and embedded networks**.
Vector is an initial registered mapping, not a synonym for Auckland coverage.
Ask the retailer to enumerate network/NSP/distributor price and loss categories,
including exclusions. Do not infer a network from a regional benchmark.

Ask for current product IDs, complete recurring components and units, GST,
meters/registers and controlled/TOU schedules including DST, eligibility, contracts,
discount conditions, dates, legacy availability and update/error notices. Unknown
components are unresolved, never zero. Source files are requested in current
EIEP14A JSON; CSV/other arrangements require discussion, not silent conversion.

The separate rights question covers normalised facts, public Git redistribution,
attribution/licensing, historical retention, raw files and screenshots. Receipt is
not a licence. No reply means publication remains blocked.

Keep a local request ledger containing only project correspondence references,
retailer, approval/send/receipt dates, agreed format, routing and rights decisions.
Do not store household details or email signatures in the tariff archive. Calculate
the response due date from the actual receipt and NZ business days, not from this
research date. Do not send duplicate requests automatically. Escalation or follow-up
also needs approval.
